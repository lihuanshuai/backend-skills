# 执行项目计划

约定 `<repo_dir>` 为目标仓库根目录，`<plan_path>` 为计划文件路径。

## 执行循环

1. 读取 `<repo_dir>/AGENTS.md`、完整计划、当前 Git 状态和相关文件，确认计划仍符合仓库事实。没有计划时先使用 `write-project-plan`；不要边猜边实现。
2. 定位用户指定步骤或首个未完成步骤，简述目标、修改范围、验证和外部副作用。用户已明确要求执行该计划时视为确认；仅提供计划、询问状态或讨论方案时，必须取得明确确认后再修改代码。
3. 按依赖顺序持续推进，每次只处理一个步骤或一组不可分割的原子改动：
   - 开始任务前把 `**状态：** 未开始` 改为 `进行中`。
   - 只修改本步骤列出的范围并复用仓库既有模式；保留无关改动和 untracked 文件。
   - 若计划与代码冲突、缺少必要步骤或继续执行不安全，先修订计划并说明影响；实质改变范围、外部契约或执行顺序时，等待用户确认。
   - 遇到 PR merge 步骤只推进到可合并状态并停止，等待用户或仓库负责人执行。
4. 立即运行计划指定的验证。失败时只在本步骤范围内修复并重跑；需要扩大范围、新授权或无法通过时停止，不得带病进入下一步。
5. 验证通过后仅局部更新计划：勾选当前 checkbox，并记录“命令、结果、关键证据”；不要粘贴完整日志。任务完成标志达成后写为 `**状态：** 已完成 (YYYY-MM-DD)`。
6. 完成当前步骤后继续下一步，除非用户要求暂停、计划设置人工门禁或需要新授权。全部任务完成后在计划头部写 `**状态：** 已完成 (YYYY-MM-DD)`。
7. 每次阶段汇报只包含当前步骤、修改文件、验证结果、阻塞点和下一步；已完成历史只引用 commit、PR、Pre 或 deploy 等标识。

## 硬约束

- 计划是执行依据，不是额外授权。生产写入、破坏性操作、发布推进及其他高风险动作仍须满足用户明确授权和对应技能门禁。
- 计划可以包含提交、推送和 PR；Agent 可推进到可审查或可合并状态，但不得自行 merge。遇到 merge 步骤必须停止并等待用户或仓库负责人。
- `docs/agent_plans/`、`.agents/plans/` 等计划文件默认只作本地执行记录，不进 stage、commit 或 PR，除非用户明确点名。
- 不为赶进度跳过验证、弱化断言或把未验证、pending、空指标写成完成；验证结果必须与实际证据一致。
