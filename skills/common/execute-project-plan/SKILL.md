# 执行项目计划

约定 `<repo_dir>` 为目标仓库根目录，`<plan_path>` 为计划文件路径。

## 执行循环

1. 读取 `<repo_dir>/AGENTS.md`、完整计划、当前 Git 状态和相关文件，确认计划仍符合仓库事实。没有计划时先使用 `write-project-plan`；不要边猜边实现。恢复执行时核对已勾选步骤、任务状态与已有验证证据；记录与实际不符时先更正，不能仅凭 checkbox 跳过工作。
2. 定位用户指定步骤或首个未完成步骤，按依赖顺序列出已完成、进行中、未开始和受阻的任务，指出当前步骤及下一处人工或外部依赖。简述目标、修改范围、验证和外部副作用。用户已明确要求执行该计划时视为确认；仅提供计划、询问状态或讨论方案时，必须取得明确确认后再修改代码。
3. 按依赖顺序持续推进，每次只处理一个步骤或一组不可分割的原子改动：
   - 开始任务前把 `**状态：** 未开始` 改为 `进行中`。
   - 在已授权目标内复用仓库既有模式，保留无关改动和 untracked 文件；必要的 import、调用方修复或计划遗漏可纳入当前步骤并更新计划。
   - 若计划与代码冲突或缺少必要步骤，按当前证据修订计划并说明影响；不改变目标、外部契约、风险或授权范围的内部顺序调整可继续。改变上述边界或继续执行不安全时，等待用户确认。
   - 遇到 PR merge 步骤只推进到可合并状态并停止，等待用户或仓库负责人执行。
   - 每完成一个可独立核验的步骤、进入耗时验证或外部等待前，向用户报告当前任务和步骤、已观察到的结果、下一步及阻塞范围；长步骤持续执行时按实际进展更新，不以预计完成时间或主观百分比代替证据。
4. 运行当前步骤适用的计划验证和仓库必跑项。失败时在已授权目标内修复必要文件并重跑受影响检查；通过后不机械重复或扩大验证。需要新授权或无法通过时，在当前任务旁记录阻塞原因、影响的步骤、已取得的证据和恢复条件；暂停依赖该结果的步骤，仍可推进已授权且不依赖该结果的任务，不得将阻塞步骤标为完成。
5. 验证通过后仅局部更新计划：勾选当前 checkbox，并记录“命令、结果、关键证据”；不要粘贴完整日志。任务完成标志达成后写为 `**状态：** 已完成 (YYYY-MM-DD)`。中断或交接前记录当前未完成步骤、已执行动作及结果、待运行的验证和恢复入口，保持未完成步骤未勾选。
6. 完成当前步骤后继续下一步，除非用户要求暂停、计划设置人工门禁或需要新授权。全部任务完成后在计划头部写 `**状态：** 已完成 (YYYY-MM-DD)`。
7. 每次阶段汇报给出已完成任务数与总任务数、当前任务和步骤、修改文件、验证结果、阻塞点和下一步；任务总数变化时说明原因。已完成历史只引用计划中的关键证据或 commit、PR、Pre、deploy 等标识，不重复完整过程。

## 硬约束

- 计划是执行依据，不是额外授权。生产写入、破坏性操作、发布推进及其他高风险动作仍须满足用户明确授权和对应技能门禁。
- 计划可以包含提交、推送和 PR；Agent 可推进到可审查或可合并状态，但不得自行 merge。遇到 merge 步骤必须停止并等待用户或仓库负责人。
- `docs/agent_plans/`、`.agents/plans/` 等计划文件默认只作本地执行记录，不进 stage、commit 或 PR，除非用户明确点名。
- 不为赶进度跳过验证、弱化断言或把未验证、pending、空指标写成完成；验证结果必须与实际证据一致。
