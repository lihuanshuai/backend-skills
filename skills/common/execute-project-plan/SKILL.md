# 执行项目计划 (Execute Project Plan)

约定 `<skill_dir>` 为本技能所在目录。

## 何时使用

- 已有实施计划文件，需要按步骤分步执行
- 用户要求「执行计划」、「分步推进」或「从第 N 步开始执行」

**前提：** 需要一份已写就的计划文件（通常由 `write-project-plan` 技能产出）。若无计划文件，应先使用 `write-project-plan` 编写计划。

## 核心流程

### 1. 确认

向用户简述计划的目标、关键步骤和验证手段，询问是否同意或有调整建议。**只有用户明确同意后方可执行，严禁在此阶段修改业务代码。**

### 2. 执行

严格按照计划分步实施：

- **单步原则**：一次只执行计划中的一个步骤（或一组强相关的原子改动）
- **计划读取最小化**：首次读取计划后，后续只读取当前步骤范围，避免反复 `cat` 全文；优先用 `sed -n '/步骤 5: 同步 PR/,/步骤 6:/p' <plan_path>` 这类范围读取命令
- **PR 合并限制**：即使计划中包含 PR 流程，Agent 也只能准备、提交、推送或创建/更新 PR；严禁自行合并 PR。必须由用户明确发起合并指令，或交由用户/仓库负责人手动合并
- **状态同步**：
  - **开始任务前**：将任务 `**状态：**` 行从 `未开始` 更新为 `进行中`
  - **每步验证通过后**：将该步骤的 `- [ ]` 更新为 `- [x]`
  - **任务完成标志达成后**：将任务 `**状态：**` 行从 `进行中` 更新为 `已完成`，记录完成日期（如 `**状态：** 已完成 (2026-05-11)`）
- **局部更新状态**：更新计划状态时只改当前步骤的 checkbox、状态行和验证记录，优先用脚本或小 patch 精确替换局部文本，避免整份计划 diff 展开
- **变更管理**：若发现原计划有误或需调整，必须先更新计划文件并告知用户，获得确认后再继续
- **改动最小化**：每步只做与该步骤相关的改动，避免顺手修改无关代码
- **历史步骤不重复解释**：已完成阶段只引用 commit、PR、pre、deploy 等标识；不要在后续步骤反复展开迁移背景或已验证过的历史细节

### 3. 验证

每步完成后必须立即验证：

- 按照计划中定义的验证方式执行
- **验证失败**：必须在本步内修复，直到验证通过。严禁带病进入下一步
- **记录结果**：在计划文件中该步骤下方追加验证结果摘要（如 `> 验证通过 (2026-05-11)：ruff check . 通过，关键输出 0 errors` 或 `> 验证失败后已修复 (2026-05-11)：pytest tests/foo.py 通过，原错误为 ...`）
- **日志摘要化**：计划里只记录「命令 + 结果 + 关键输出」，不要粘贴完整 CI、DAE、pre、deploy 或长测试日志；完整日志只在必要时保留为外部链接、文件路径或运行编号

### 4. 推进

- 任务完成标志达成后，更新任务状态为 `已完成 (日期)`，向用户汇报进度
- 全部任务完成后，在计划文件头部追加 `**状态：** 已完成 (日期)`
- **阶段性汇报收敛**：每步只回报当前步骤、已改文件、验证结果、阻塞点、下一步；不要重复解释历史背景或展开完整日志

## 核心原则

- **先确认，后执行**：没有用户确认，不动代码
- **严格按计划执行**：不做计划外的改动
- **一步一验证**：每步必验证，验证必通过
- **改动最小化**：每步只做与该步相关的改动
- **上下文最小化**：计划读取、计划更新、验证记录和阶段性汇报都只围绕当前步骤，避免反复读写或转述整份计划
- **禁止自行合并 PR**：计划执行到 PR 阶段时，最多推进到可审查/可合并状态；是否合并必须等待用户或仓库负责人确认
