# 编写项目实施计划 (Write Project Plan)

## 何时使用

- 拿到需求/规格文档后、动手编码前
- 多步骤任务需要拆解为可执行计划
- 需求涉及多个文件、模块或子系统

## 核心流程

### 1. 范围检查

若需求/规格涵盖多个独立子系统，应建议拆分为多个独立计划——每个子系统一份。每个计划必须能独立产出可工作、可测试的软件。

### 2. 文件结构规划

在定义任务之前，先梳理需要创建或修改的文件及其职责：

- 每个文件应有单一明确的职责，边界清晰、接口明确
- 优先小而聚焦的文件，而非大而全的文件
- 变动相关的文件应放在一起，按职责拆分而非按技术层拆分
- 在既有代码库中遵循已有模式；若修改的文件已臃肿，可在计划中包含拆分步骤

### 3. 需求理解与确认

**编写计划前，必须充分理解需求：**

- 阅读需求文档、相关代码、现有实现
- 识别需求中的不确定点、歧义或多重选择
- **不确定处必须向用户澄清，由用户决策** —— 禁止凭假设替用户选择

**常见需澄清的场景：**
- 多个可行方案（如技术选型、实现策略）
  - 当存在多种技术实现方案时，列出各方案优劣，由用户决策
  - 当接口设计存在多种选择时，提供候选方案供用户选择
  - 当项目结构或代码位置不明确时，向用户确认而非自行推断
- 边界条件未定义（如空值处理、异常场景）
- 与现有系统的冲突或兼容性问题
- 需求优先级与范围取舍

**原则：不确定点或有多种候选方案时，必须向用户确认，禁止假设填充**

### 4. 任务拆解

**每个步骤是一个原子动作（2-5 分钟）：**

- "写失败测试" — 一个步骤
- "运行测试确认失败" — 一个步骤
- "写最小实现使测试通过" — 一个步骤
- "运行测试确认通过" — 一个步骤
- "提交" — 一个步骤

### 5. 编写计划文档

计划保存至 `docs/plans/YYYY-MM-DD-<feature-name>.md`（用户偏好可覆盖此默认路径）。

常见计划类型：
- **功能需求**：明确需求 → API 草稿 → mock → 分步实现 → 联调修复
- **代码迁移**：
  - 策略 A（先改后上）：依次修改并 commit，全部完成后 cherry-pick 逐阶段提交 PR —— 适合长时间运行、需保持分支稳定的迁移
  - 策略 B（逐步改上）：每完成一个子任务即提交 PR 并上线 —— 更可控，风险分散
- **RPC 接口变更**：涉及多项目协作（如服务端修改 PIDL/Thrift + 客户端升级依赖）—— 创建计划前必须理解所有涉及项目的代码结构；每个步骤需明确标注执行项目（如「在 service 项目...」「在 client 项目...」），并考虑版本兼容性

计划文档结构详见 `<skill_dir>/references/plan-document-structure.md`，包含：
- 文档头部格式（目标、架构、技术栈）
- 任务格式（状态、完成标志、文件列表、步骤）
- 状态机制说明

### 5. 零占位符原则

**以下写法是计划失败——绝不允许：**

- "TBD"、"TODO"、"稍后实现"、"后续补充"
- "添加适当的错误处理"、"添加验证"、"处理边界情况"
- "为上述代码编写测试"（而不给出实际测试代码）
- "与任务 N 类似"（必须重复代码，读者可能按任意顺序阅读任务）
- 步骤只描述做什么而不展示怎么做（代码步骤必须包含完整代码）
- 引用未在任何任务中定义的类型、函数或方法

### 6. 自审检查

计划编写完成后，对计划进行自我审查：

**1. 需求覆盖度**：逐条检查需求/规格的每个部分/要求，能否找到对应的任务？列出遗漏。

**2. 占位符扫描**：搜索计划中是否出现「零占位符原则」中列出的禁止模式，发现即修复。

**3. 类型一致性**：检查后续任务中使用的类型、方法签名、属性名是否与前面任务中的定义一致。例如任务 3 中写 `clearLayers()` 而任务 7 中写 `clearFullLayers()` 即为错误。

发现问题则就地修复。若发现需求条目无对应任务，补充任务。

### 7. 执行交接

计划完成后，建议用户使用 `execute-project-plan` 技能执行计划。

## 核心原则

- **零占位符**：每个步骤必须包含完整内容，不允许模糊描述
- **精确路径**：始终使用完整文件路径
- **完整代码**：每个代码步骤必须展示完整代码
- **精确命令**：每个命令步骤必须给出具体命令与预期输出
- **DRY、YAGNI、TDD、频繁提交**

## 注意事项

- 需求不清晰时，应先向用户澄清再编写计划，而非凭假设填充
- 保持与项目既有代码风格和模式一致
