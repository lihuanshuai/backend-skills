# 编写项目实施计划

约定 `<skill_dir>` 为当前技能目录，`<repo_dir>` 为目标仓库根目录。

## 流程

1. 建立事实：读取需求、`<repo_dir>/AGENTS.md`、相关实现、测试、配置和依赖调用方。不得只根据需求文本推测仓库结构或接口。
2. 确定边界：先列出受影响的项目、文件职责、接口和依赖顺序。多个可独立交付的子系统拆成多份计划；跨仓或 RPC 任务在每项中标明项目、兼容顺序和升级节点。
3. 处理不确定性：优先从代码和文档消除。低风险推断作为假设写入计划；若选择会实质改变外部契约、范围或执行顺序且证据无法判定，先请用户决策。
4. 写入计划：读取 `<skill_dir>/references/plan-document-structure.md`，按其唯一格式写入用户指定路径；未指定时使用 `<repo_dir>/docs/agent_plans/YYYY-MM-DD-<feature-name>.md`。
5. 组织任务：先写 3–7 条任务总览，再按依赖顺序写可独立验证的编号任务。行为代码优先采用失败测试、最小实现、通过测试、扩大验证、提交的闭环；文档、配置或无法合理先写测试的改动使用最小且真实的验证，不虚构失败测试。
6. 自审并修复：逐条映射需求到任务，核对路径、符号、签名、依赖顺序、命令和预期结果，扫描占位符与前后矛盾。
7. 交付计划路径、关键决策和仍待用户决定的阻塞项；建议后续使用 `execute-project-plan`。本技能只写计划，不实施业务改动。

## 输出契约

- 计划必须让零项目上下文的工程师仅凭文件内容即可执行，不依赖当前对话中的隐含信息。
- 每个任务必须包含状态、客观完成标志、精确文件与符号、按序步骤、验证命令和可观察的预期结果。
- 代码步骤必须给出可直接落地的完整代码；禁止省略号、`TBD`、`TODO`、“同上”“类似任务 N”或“添加适当处理”等占位表达。
- 仓库事实、现有输出和外部状态必须有证据；未来步骤的预期结果应明确标为预期，不得伪装成已验证事实。

## 硬约束

- 遵循现有架构、代码风格和仓库命令；不要为满足模板编造文件、API、测试或发布步骤。
- 计划可包含提交、推送和 PR 步骤，但不得把需要用户或仓库负责人执行的 merge 写成 Agent 可自行完成的动作。
- 除计划文件及其目录外不修改代码、配置或运行时状态；除非用户另行要求，不提交或推送计划。
