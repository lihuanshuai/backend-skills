# 编写项目实施计划 (Write Project Plan)

## 何时使用

- 拿到需求/规格文档后、动手编码前
- 多步骤任务需要拆解为可执行计划
- 需求涉及多个文件、模块或子系统

## 核心流程

### 1. 范围检查

若需求/规格涵盖多个独立子系统，应建议拆分为多个独立计划——每个子系统一份。每个计划必须能独立产出可工作、可测试的软件。

### 2. 文件结构规划

在定义任务之前，先梳理需要创建或修改的文件及其职责：

- 每个文件应有单一明确的职责，边界清晰、接口明确
- 优先小而聚焦的文件，而非大而全的文件
- 变动相关的文件应放在一起，按职责拆分而非按技术层拆分
- 在既有代码库中遵循已有模式；若修改的文件已臃肿，可在计划中包含拆分步骤

### 3. 任务拆解

**每个步骤是一个原子动作（2-5 分钟）：**

- "写失败测试" — 一个步骤
- "运行测试确认失败" — 一个步骤
- "写最小实现使测试通过" — 一个步骤
- "运行测试确认通过" — 一个步骤
- "提交" — 一个步骤

### 4. 编写计划文档

计划保存至 `docs/plans/YYYY-MM-DD-<feature-name>.md`（用户偏好可覆盖此默认路径）。

参考样板（位于 `<skill_dir>/references/`）：
- **功能需求**：`<skill_dir>/references/feature-implementation-template.md` — 明确需求 → API 草稿 → mock → 分步实现 → 联调修复，以 PR 合并为完成标志
- **代码迁移**：`<skill_dir>/references/code-migration-template.md` — 逐步实现并 commit，完成后 cherry-pick 逐阶段提交 PR

**计划文档头部（必须）：**

```markdown
# [功能名称] 实施计划

**目标：** [一句话描述最终产出]

**架构：** [2-3 句说明实现思路]

**技术栈：** [关键技术/库]

---
```

**每个任务格式：**

```markdown
### 任务 N: [组件名称]

**状态：** 未开始

**完成标志：** [具体验证条件，如 "PR 合并到 main"、"全量测试通过"]

**文件：**
- 创建: `exact/path/to/file.py`
- 修改: `exact/path/to/existing.py:123-145`
- 测试: `tests/exact/path/to/test.py`

- [ ] **步骤 1: 写失败测试**

\`\`\`python
def test_specific_behavior():
    result = function(input)
    assert result == expected
\`\`\`

- [ ] **步骤 2: 运行测试确认失败**

运行: `pytest tests/path/test.py::test_name -v`
预期: FAIL，报错 "function not defined"

- [ ] **步骤 3: 写最小实现**

\`\`\`python
def function(input):
    return expected
\`\`\`

- [ ] **步骤 4: 运行测试确认通过**

运行: `pytest tests/path/test.py::test_name -v`
预期: PASS

- [ ] **步骤 5: 提交**

\`\`\`bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
\`\`\`
```

**状态机制：**

- **任务级状态**（`**状态：**` 行）：`未开始` → `进行中` → `已完成`，执行时由 `execute-project-plan` 技能更新
- **步骤级状态**（checkbox）：`- [ ]` → `- [x]`，每步验证通过后勾选
- **完成标志**：每个任务必须声明具体的完成条件，禁止模糊描述（如 "功能实现"），必须可客观判定（如 "PR owner/repo#123 合并到 main"、"pytest tests/ 全量通过"）

### 5. 零占位符原则

**以下写法是计划失败——绝不允许：**

- "TBD"、"TODO"、"稍后实现"、"后续补充"
- "添加适当的错误处理"、"添加验证"、"处理边界情况"
- "为上述代码编写测试"（而不给出实际测试代码）
- "与任务 N 类似"（必须重复代码，读者可能按任意顺序阅读任务）
- 步骤只描述做什么而不展示怎么做（代码步骤必须包含完整代码）
- 引用未在任何任务中定义的类型、函数或方法

### 6. 自审检查

计划编写完成后，对计划进行自我审查：

**1. 需求覆盖度**：逐条检查需求/规格的每个部分/要求，能否找到对应的任务？列出遗漏。

**2. 占位符扫描**：搜索计划中是否出现「零占位符原则」中列出的禁止模式，发现即修复。

**3. 类型一致性**：检查后续任务中使用的类型、方法签名、属性名是否与前面任务中的定义一致。例如任务 3 中写 `clearLayers()` 而任务 7 中写 `clearFullLayers()` 即为错误。

发现问题则就地修复。若发现需求条目无对应任务，补充任务。

### 7. 执行交接

计划完成后，建议用户使用 `execute-project-plan` 技能执行计划。

## 核心原则

- **零占位符**：每个步骤必须包含完整内容，不允许模糊描述
- **精确路径**：始终使用完整文件路径
- **完整代码**：每个代码步骤必须展示完整代码
- **精确命令**：每个命令步骤必须给出具体命令与预期输出
- **DRY、YAGNI、TDD、频繁提交**

## 注意事项

- 需求不清晰时，应先向用户澄清再编写计划，而非凭假设填充
- 保持与项目既有代码风格和模式一致
